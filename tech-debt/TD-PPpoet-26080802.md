**Severity:** Medium

`src/tools/blogger-auth.js`'s `waitForCode()` (`:336-387`) handles two
outcomes from the OAuth redirect: a `code` (success) branch that checks
`returnedState !== expectedState` before doing anything else (`:356-362`),
and an `error` branch (`:345-351`) that does neither — it never checks
`state`, and writes the raw `error` query parameter straight into its HTML
response with no escaping: `` res.end(`<html>...<p>${error}</p>...`) ``.

The server binds to `127.0.0.1` only (`redirectUri =
\`http://localhost:${port}\``), so this needs code already running on the
same machine to exploit, but it accepts any GET request matching the URL
shape from any local process during the short window the script waits for
the redirect — no `state` value required, since the error path skips that
check. A local attacker (or a stray browser tab) can send
`GET /?error=<img src=x onerror=alert(1)>`, get it reflected into a page
rendered in the user's browser, and simultaneously abort the legitimate
auth flow. Bounded blast radius (loopback-only, one-shot server that closes
itself after the first matching request) is why this is Medium rather than
higher, per the review's "harm escapes the project's boundary" test — it
doesn't, here.

`test/blogger-auth.test.js:78-92` covers only the `code`/state-mismatch
paths; the `error` branch's HTML output is untested.

**Suggested fix:** HTML-escape `error` before interpolating it into the
response (an existing helper such as `aggregate-render-core.js`'s
`escapeHtml` can likely be reused or its pattern copied), and apply the
same `returnedState` check to the `error` branch that the `code` branch
already has. Add a test covering both.
