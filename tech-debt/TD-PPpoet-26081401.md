---
id: TD-PPpoet-26081401
title: Blogger sync composes an empty publish date instead of failing on an un-normalisable poem date
status: open
filed: 2026-08-14
---

**What.** `src/tools/sync-blogger.js`'s poem loop normalises each poem's date
with `toISODate(raw.date) || ''`, so any date `toISODate()` cannot parse —
missing, an invalid `Date` object, or a string that is not `yyyy-mm-dd` (e.g.
an already-formatted `DayOfWeek, DD Month YYYY` display string) — silently
becomes the empty string and the sync proceeds as though that were a date.
Nothing warns, and no counter records it. Raised in the review of PR #173
(https://github.com/Poetic-Poems/poetic/pull/173#issuecomment-5289347621) as
follow-on work.

**Why it matters.** The empty string reaches three places, and is wrong in
each:

- `composePost()` builds `published: "T00:00:00Z"`, which is not a timestamp.
  `new Date("T00:00:00Z")` is an `Invalid Date`, so `postNeedsUpdate()`'s
  instant comparison is `NaN !== <anything>` → always true: the poem is
  reported as "updated" and PUT on every single run, for ever, never
  converging.
- `syncPoem()`'s dated-title trick takes the day as `isoDate.slice(8, 10)`,
  gets `''`, and creates the post titled `" <title>"` with a leading space.
  Blogger derives the permalink from the creation-time title and that
  permalink is sticky, so a wrong one is permanent.
- Whatever Blogger itself does with `published: "T00:00:00Z"` is unattractive
  both ways. Rejected: the `catch` in `main()` aborts the whole sync at an
  arbitrary poem, part-way through mutating a live blog, with an API error
  that does not name the poem that caused it. Accepted-and-ignored: the post
  quietly carries a publish date nobody chose.

This is not a regression from PR #173. The inline expression it replaced,
`String(raw.date || '')`, passed a display string through verbatim and
composed `published: "Friday, 15 March 2024T00:00:00Z"` — equally broken,
just differently shaped, and it fell into the same `''` for a missing date.
What is absent in both versions is the failure.

Exposure today is low but not nil. `docs/YAML-SCHEMA.md` specifies `date` as
a required `yyyy-mm-dd` field, and no poem in the corpus, the examples or the
test fixtures carries a display-format or missing date. Nothing enforces
that, though — the sync is not gated by any schema validation — and the
codebase does contemplate display-format dates surviving into poem data:
`toISODate()`'s own docstring names "already a `DayOfWeek, DD Month YYYY`
display string" as a case it returns `null` for, and
`formatDateForDisplay()` defensively tolerates that shape on input.

**Where.** `src/tools/sync-blogger.js` — the `toISODate(raw.date) || ''` line
in `main()`'s poem loop (the origin), plus `composePost()` and `syncPoem()`
(where the consequences land); `test/sync-blogger.test.js`.

`src/tools/aggregate-render-core.js` and `src/tools/build-all-poems.js` apply
the same `toISODate(...) || ''` fallback, but on the render side an empty
`isoDate` only degrades a data island's client-side sort. Leave those as they
are: this item is about the path that mutates a live blog.

**Suggested fix.** Make an un-normalisable date a visible per-poem failure
instead of a silent empty one: warn, naming the YAML file and the offending
value; count it; skip the poem; and set `process.exitCode = 1` at the end of
the run so an unattended sync does not exit 0 on a poem it never synced.
Report the count in the closing `Blogger sync: … created, … updated, …`
summary line.

Two constraints the fix must respect:

1. **A skip must not read as a removal.** A skipped poem's slug must still be
   added to `currentSlugs`, or the removal pass will find its live post no
   longer among the current slugs and draft or delete it — turning a bad date
   into content loss. That forces the check to sit after `loadPoemData()`
   (the slug comes from `data`, not `raw`) and after the `--only` filter,
   rather than where the `toISODate()` call is today. The same file already
   holds the precedent that the removal pass is unsafe on an incomplete slug
   set: the `--only` branch skips that pass entirely, for exactly this
   reason.
2. **`--dry-run` must surface it.** The dry run is the only preview of a
   sync; a warning that appears only on the live run arrives after the
   mutations have started.

An alternative worth weighing when this is picked up: validate every poem's
date up front, before the first mutation, and abort the run if any fails —
nothing is left half-synced, at the cost of one bad poem blocking every other
poem. Either way, the property to preserve is that `''` never reaches
`composePost()`.

Referenced from: poetic PR #173's review comment (linked above), which
identified the behaviour while reviewing the de-duplication asked for by
TD-PPpoet-26080809 and recommended this as separate follow-on work, since it
is a behaviour change rather than a de-duplication.
