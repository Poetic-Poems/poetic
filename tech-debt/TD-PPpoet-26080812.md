**Severity:** Low

`src/tools/blogger-auth.js` makes three real network calls —
`exchangeCodeForTokens()` (`:174-178`), `lookupBlogId()` (`:192-194`),
`listMyBlogs()` (`:217-219`) — all plain `fetch(url, init)` with no
`signal`/`AbortSignal.timeout()` and no retry, unlike `sync-blogger.js`'s
shared `fetchWithRetry()` wrapper (30s timeout + single retry,
`sync-blogger.js:405-418`) used for the identical Google OAuth token
endpoint and Blogger API.

**Why it matters.** Low risk — this is a one-time interactive helper a
maintainer runs manually (`npm run blogger:auth`) and can Ctrl-C if it
hangs, not an unattended/CI path (CI only ever runs `sync-blogger.js`,
which does have the timeout). Still, a hung DNS resolution or a Google
endpoint that accepts the connection but never responds would leave the
script hanging indefinitely mid-flow — e.g. after the loopback server
already received the auth code, before the token exchange completes — with
no indication to the person waiting that anything is wrong, and it's an
easy-to-miss inconsistency against the timeout discipline the sibling file
already established for the same three endpoints' Google-API counterparts.

**Suggested fix:** Reuse (or extract to a shared helper) `sync-blogger.js`'s
`fetchWithRetry`/timeout pattern for these three calls — retry is optional
here (a one-shot interactive tool), but the timeout alone would bound the
hang.
