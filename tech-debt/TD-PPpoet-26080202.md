---
id: TD-PPpoet-26080202
title: yaml-to-poem writes version/segment/postscript labels as raw HTML instead of reverse-converting them, corrupting label markup on the next parse
status: open
filed: 2026-08-02
---

Discovered while verifying TD-PPpoet-26080201's fix against the real
`fragments-and-unity` corpus (75 poems, pinned at the commit
TD-PPpoet-26080201 was filed against): `easter-joy-immanuel-is-his-name.poem`
is still unstable between the first and second `.poem` → YAML → `.poem`
pass, for a cause distinct from all three TD-PPpoet-26080201 fixed.

`PoemParser#parseHeader()`/`parseVersions()` etc. run a version's, segment's,
or postscript note's label through `convertMarkup()` before storing it —
`version.label = convertMarkup(this.substituteVariables(label));`
(`src/tools/poem-parser.js`) — so `label` in the YAML data is already
rendered HTML (spans, smart quotes, emphasis, links), exactly like
`segment.lines`/`postscript.content`.

But on the reverse side, `YamlToPoemConverter#formatLabelLine()`
(`src/tools/yaml-to-poem.js`) writes that HTML straight into the `.poem`
output — `return params ? base + this.formatParamList(params) : base;` with
`base` built directly from the raw `label` string — never passing it through
`convertHtmlToPlainText()`/`convertSegmentHtmlToPlainText()`/
`stripSegmentHtmlTags()` the way every other HTML-bearing field is. Every
other writer method un-renders its HTML back to `.poem` markup syntax before
writing it; label writing is the one place that doesn't.

Concretely, on `easter-joy-immanuel-is-his-name.poem`, a version label built
from variable substitution assembles a `/.class{...}` span:

```
={a}=/.poetic-alternatives.25
{{ Song arrangement, with an added verse and pre-chorus${a}{ (2025)}${b}{, ... } }}
```

`${a}{ (2025)}` expands to `/.poetic-alternatives.25{ (2025)}`, which
`convertMarkup()` renders to `<span class="poetic-alternatives 25"> (2025)</span>`
in `version.label`. `formatLabelLine()` writes that `<span class="...">` tag
verbatim into the regenerated `.poem` file's `{{ }}` line. On the next parse,
`convertMarkup()` runs over that literal `<span class="poetic-alternatives 25">`
text as ordinary label content — its own quote-pairing regex
(`text.replace(/"([^"]+)"/g, '&#8220;$1&#8221;')`) doesn't know these `"`
characters are an HTML attribute, not the poem author's prose, and smart-quotes
them: `class=&#8220;poetic-alternatives 25&#8221;`. The label keeps this
corruption from then on (stable, but wrong) — it doesn't grow further, but it
never recovers the original `.poem`-syntax form either.

Any label using span/emphasis/strong/strikethrough/link markup or smart
quotes is affected, not just this one poem — it's the only one in the
`fragments-and-unity` corpus whose label happens to use markup elaborate
enough to trigger a visible corruption (a bare `<em>`/`<strong>` tag with no
attribute quotes would silently write back as literal HTML too, just without
the second-pass mangling that made this instance visible).

Where: `src/tools/yaml-to-poem.js` — `formatLabelLine()`, and the
`writeVersions()`/`writeSegmentParts()`-equivalent call sites that pass a raw
`label` into it (version label, segment label, postscript label).

Suggested fix: route `label` through the same HTML-to-plain-text conversion
the field's own content already gets before calling `formatLabelLine()` —
labels use the same WYSIWYG dialect as segment lines (`convertMarkup()`), so
`convertSegmentHtmlToPlainText()`/`stripSegmentHtmlTags()` is probably the
right reverse path, not `convertHtmlToPlainText()` (that one is for the GFM
analysis/postscript dialect). Add a fixture under `test/fixtures/round-trip/`
with a label carrying inline markup (at minimum a span and a smart-quote
pair) to cover it.
