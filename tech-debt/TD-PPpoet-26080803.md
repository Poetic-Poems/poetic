**Severity:** Medium

`TD-PPpoet-26072901` documented mtime-comparison flakiness ("roughly one
run in three to five locally (WSL2)") in `test/poem-to-yaml.test.js` and
`test/poem-to-raw-cli.test.js`, and PR #133 fixed both by backdating the
output file's `mtimeBefore` baseline via `fs.utimesSync` before capturing
it, so a real-time write afterward is guaranteed to compare later than the
backdated baseline.

Two tests in `test/build-poems.test.js` (`:101-123`, `:125-171`) have the
exact same shape and were never fixed. They already backdate the *input*
file's mtime (since commits `a84e929`/`576788c`, 2026-07-11/12), but
`pageMtimeBefore` is still captured from the output file's real,
non-backdated wall-clock mtime (`:110`, `:154`), then compared with a
strict `>` against a second real-time write moments later (`:120`, `:166`)
— the same timing/filesystem-dependent flake TD-PPpoet-26072901 already
fixed elsewhere, left open in this one file. `TD-PPpoet-26072901` itself is
scoped only to `poem-to-raw`/`poem-to-yaml` and does not cover this file;
it should not be reopened for this — this is a new, adjacent item.

**Suggested fix:** Apply the identical `fs.utimesSync`-backdating pattern
from `test/poem-to-yaml.test.js:118-120`/`test/poem-to-raw-cli.test.js:127-129`
to both tests in `test/build-poems.test.js`.
