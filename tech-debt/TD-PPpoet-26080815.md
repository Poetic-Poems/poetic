**Severity:** Low

Three related gaps in the same `$ref`-resolution/caching subsystem
(`poem-render.js`, `build-all-poems.js`, `serve-static.js`), bundled
because a fix to one likely touches the same functions as the others:

1. **`build-all-poems.js`'s "skip if up to date" fast path still fully
   parses the whole corpus (and its `$ref` graph) every run.**
   `build-all-poems.js:466-476` computes the staleness-check `sources` set
   via `collectRefFiles()` (`poem-render.js:234-242, 188-221`), which parses
   every poem's YAML and recursively `yaml.load()`s every `$ref` target —
   unconditionally, even on the common "nothing changed, skip" path.
   Negligible today (3-poem example corpus); the unskippable parse cost
   grows linearly with a consumer repo's poem count and `$ref` fan-out.

2. **`collectRefFiles()` re-parses a shared `$ref` target once per
   referencing poem instead of reusing the shared cache.**
   `poem-render.js:206-211` reads a `$ref` target via a bare `yaml.load`,
   not `readYamlCached()`, even though the caller (`refFilesForPoem()`,
   `:234-242`) is itself handed the shared `yamlCache` from
   `build-all-poems.js:465`. `collectRefFiles`'s own `seen` Set (`:188`) is
   freshly created per call, so a partial referenced by N poems gets parsed
   N times during the sources-computation pass. Compounds (1)'s cost by a
   further factor — a perverse incentive against poem authors using `$ref`
   partials to avoid duplication, the exact feature it's meant to
   encourage.

3. **`serve-static.js`'s long-running `/all-poems` endpoint never
   invalidates `poem-render.js`'s process-lifetime `$ref` cache.**
   `poem-render.js:37`'s module-level `refCache` is evicted only via
   `clearRefCache()` (`:286-288`), called by `build-poems.js` (a fresh
   process each invocation, a no-op there) and by tests — `serve-static.js`
   never calls it. Its `/all-poems` route (`:235-253`) re-renders on every
   request via `resolveRefs()`, which always consults the shared,
   never-cleared cache. `serve-static.js` is designed as a long-running
   process (graceful-shutdown handling, `npm run stop`), and `npm run
   build:all` starts it right after a build — so a poet iterating on a
   shared `$ref`'d partial while the dev server is up sees the *first*-
   resolved version of that partial on every subsequent `/all-poems`
   reload, however many times the source changes, until the server is
   restarted. Undocumented and untested (`test/serve-static.test.js` has no
   test touching `/all-poems`). This is the item with the most user-visible
   impact of the three and should not be dropped if effort needs trimming.

**Suggested fix:** Thread the caller's cache into `collectRefFiles`'s
`yaml.load` call (via `readYamlCached`) to fix (2) directly. Persist the
last-known ref graph alongside the build manifest (invalidated only when a
poem's own mtime/size changes) to let an unchanged corpus skip the parse
pass entirely, fixing (1). For (3), either have `resolveRefs()` accept a
request-scoped cache for the live-render path instead of the module-level
one, or have `serve-static.js`'s `/all-poems` handler call
`clearRefCache()` at the top of the route — trading cross-request
memoisation for correctness, matching the fact every other route already
re-reads from disk per request.
