# Summary

## What this project is

Poetic is a Node.js framework — not a poem collection — for authoring poems in a plain-text `.poem` format, converting them to a YAML intermediate representation, and rendering them to HTML via a Pug template for publication on GitHub Pages, with optional syncing to a Blogger blog. Consumer repositories (e.g. "Fragments & Unity") pull the framework's build scripts, templates, and editor tooling in via `scripts/sync-framework.sh`, pinning a version with `.poetic-version`; poem source files themselves are never touched by that sync.

The stack is plain CommonJS Node.js (`engines.node >=22`), with four runtime dependencies (`js-yaml`, `markdown-it`, `pug`, `js-beautify`) and ESLint plus `c8` as the dev-side toolchain. The codebase is compact — roughly 9,200 lines across 28 hand-written files in `src/tools/`, plus a 203-line filesystem-free "core" shared between the Node build path and a browser bundle (`src/browser/`, published as the `poetic/browser` export). It is an actively developed, solo-maintained project (100% of commit history traces to one person, working partly through AI coding agents under an elaborate documented multi-agent workflow) at v6.1.1, with three prior full project reviews (2026-07-07, 2026-07-11, 2026-07-21), all substantially remediated — going into this review, `TECH-DEBT.md`'s Ledger carried only one open item.

## Overall assessment

The project is in strong, still-improving health, and this is the cleanest starting point any of the four reviews has had. Since 2026-07-21, 30 commits landed, including a further wave of dependency/security hygiene (a js-yaml DoS fix, verified via the golden test suite to not have regressed the earlier v4→v5 timestamp-quoting risk), a genuine architectural decomposition (`poem-parser.js` split into three focused, cycle-free, individually-tested modules), and continued fidelity fixes to the `yaml-to-poem.js` reverse converter. Every automated check this review ran fresh came back clean: 574 tests (570 passing, 4 environment-conditional skips), `npm run lint`, the trailing-whitespace gate, `npm audit` (0 vulnerabilities), and a full build plus artefact check. CI is confirmed actually green on `main`, not just configured to look that way.

Against that strength, this review found two High-severity gaps, both about a guarantee that looks stronger on paper than it is in practice. First, the changelog-bump CI check the 2026-07-21 review recommended and a subsequent PR added is not in the branch-protection ruleset's required-checks list, so it can be bypassed by a squash-merge past a red X — undermining the exact guarantee CLAUDE.md's "Release process" section claims it provides. Second, `sync-blogger.js`'s `main()` — the one function that actually decides, for every poem, whether to create, update, or delete a live Blogger post on every push to `main` — has zero test coverage, in a file where every other piece of logic is thoroughly unit-tested; this is the project's single largest gap between "code that's well-factored" and "code that's proven correct," precisely because it's also the code with the widest blast radius (a real, public, third-party service). A related Medium finding compounds the second: the retry logic that wraps every Blogger API call, sound for every idempotent call, can duplicate-post a poem if a `createPost` request's response is lost after Blogger has already processed it. A further Medium finding — two config-path resolvers (`footer.source`, `blogger.template`) that bypass the project's own path-containment guard, unlike every other place that guard exists to protect — is a real, if narrow-blast-radius, content-disclosure gap gated behind the same write access that already controls published output. No Critical finding exists anywhere, and the two High findings are both about hardening an already-working system rather than fixing something actively broken.

## Headline strengths

- Every automated check re-run fresh for this review passed cleanly: 574 tests (570 pass, 4 skip), lint, `npm audit` (0 vulnerabilities), the whitespace gate, and a full build with artefact verification [scope and method].
- The `poem-parser.js` → three-module split (commits #104/#106/#108) is a genuine decomposition, not a relocation: no cycles, each module independently tested, and the fix for the one previously-known quadratic hotspot moved intact through the refactor [F-ARCH strengths, F-PERF strengths].
- CI is unusually well-documented and its trust boundaries are handled correctly throughout (fork PRs never reach `deploy` or Blogger-sync jobs; commit-format validation shares one source of truth between the local hook and CI) [F-CI strengths, F-SEC strengths].
- Both accessibility defects the 2026-07-21 review fixed were independently re-verified this review as still genuinely fixed by direct inspection, not by trusting the tech-debt Ledger [F-UX strengths].
- The self-review/single-maintainer/bus-factor disclosure this project added to its own docs after the 2026-07-21 review was re-checked against live GitHub API state (not just re-read) and is still accurate today [F-GOV strengths].

## Headline risks

- `changelog-check`'s CI gate is not actually enforced by branch protection, so a version bump can land on `main` without a matching `CHANGELOG.md` entry despite the check existing specifically to prevent that [F-CI-01].
- `sync-blogger.js`'s `main()` — the code that mutates a live public blog on every relevant push — has zero test coverage, and its retry logic can duplicate-post under an uncommon but real network-timing failure [F-TEST-01, F-OPS-01].
- Two config-supplied file paths (`footer.source`, `blogger.template`) bypass this project's own path-containment guard, creating a content-disclosure primitive for anyone who can already edit a consumer repo's `.poetic-config.yaml` [F-SEC-01].
- `serve-static.js`'s actual HTTP request handler — including where its path-traversal guard is wired in — has never run under test, only its extracted pure helpers have [F-TEST-02].
- A prior tech-debt item was marked "resolved" while its own closing commit admitted one part was deliberately left undone, and no new entry tracked that residual piece — a small but instructive gap in the process this project otherwise relies on to keep debt from being silently lost [F-GOV-01].

## Scope and method

Exhaustive: all of `src/tools/` (28 files) and `src/browser/` (2 files), `TECH-DEBT.md`, `CLAUDE.md`, every `.github/workflows/*.yml`, and every top-level doc (`README.md`, `CHANGELOG.md`, `SECURITY.md`, `CODEOWNERS`, licence files). Representative sampling: `test/` (34 files) — the largest and most safety-relevant suites (`sync-blogger`, `path-guard`, `build-poems`, `golden`, `yaml-to-poem-roundtrip`, `serve-static`, `blogger-auth`, `poem-to-raw`) were read in full; the remainder was skimmed for structure and cross-checked via a fresh coverage run. `docs/` was spot-checked against current code rather than read word-for-word, including live-testing five documented procedures end-to-end. `editors/vim/` was checked structurally and its install script actually run against a scratch `$HOME`.

Tools run fresh this review: `npm ci`, `npm test`, `npm run lint`, `npm run check`, `npm audit` (default and `--omit=dev`), `npm run build` + `npm run check:build`, `npm run coverage` (c8). GitHub-side state was checked live via `gh api`/`gh run list`/`gh pr list` rather than assumed from CLAUDE.md's description of it — this is how the branch-ruleset gap (F-CI-01) and the governance disclosure's continued accuracy (F-GOV strengths) were established as *current* fact, not carried over from the prior review. A full git-history secret scan was performed in the 2026-07-21 review and is not repeated in full here; this review instead scanned the 30 commits landed since then, plus a fresh working-tree grep, and found nothing new.

Not covered: consumer repositories (e.g. "Fragments & Unity") that actually exercise this framework at real poem-collection scale — this repo carries only two example poems, so claims about behaviour "at scale" (e.g. F-PERF-01/F-PERF-02) are necessarily judged from the code's structure rather than observed real-world runtimes. Dimension-review work was parallelised across six subagents grouped by dimension pairs/triples; each subagent's findings were independently persisted and then consolidated by the lead reviewer, who also performed the tooling verification and GitHub-API checks above directly.

A note on this review's own process: partway through, the working environment suffered several transient filesystem interruptions (the review's own working directory briefly became inaccessible, and two dimension-review subagents' assigned clones were wiped mid-task). None affected the repository's committed state or this review's findings — subagents recovered by re-cloning the same commit and the lead reviewer recovered by re-creating lost worknotes from conversation context and committing checkpoints more frequently thereafter — but it is recorded here for transparency, since a reader comparing this review's worknotes timestamps to its findings might otherwise wonder about the gaps.
