# Summary

## What this project is

Poetic is a Node.js (>=22) framework for authoring poems in a custom `.poem` plain-text format, converting them to YAML, and rendering them to static HTML via a Pug template, for publication to GitHub Pages and, optionally, a Blogger blog. It is a single-maintainer, MIT-licensed framework repository — poem *collections* are separate consumer repositories that pull framework files in via `scripts/sync-framework.sh`, so this repo's own `src/poems/` holds only example/test poems, not real content.

The codebase is medium-sized (~10,300 lines of source, matched almost 1:1 by ~10,200 lines of test) and mature: this is its **sixth** full project review, following five prior reviews (2026-07-07, -11, -21, -26, -31) that between them raised, tracked, and resolved 76 tech-debt items — 73 resolved, 2 not-debt, and, going into this review, 1 open. The tooling reflects that maturity: a per-item tech-debt register with its own CI-gated consistency checker, license-compatibility and accessibility checks, Dependabot, CodeQL, and a squash-only branch-protection ruleset with required status checks that this review independently confirmed still matches the register's own record of it.

## Overall assessment

Poetic remains in strong health, and the trend line since the last review is genuinely positive. Every automated gate re-run from scratch this session passed cleanly: 703 tests (699 pass, 4 deliberately skipped), lint, `npm audit` (0 vulnerabilities, both with and without dev dependencies), the whitespace gate, the licence-compatibility check, the tech-debt register's own consistency checker, and a full build — with coverage at 85.36% lines against an 80% CI-enforced floor. The 20 commits landed since the last review (2026-07-31) show a continued pattern of same-day-to-few-day fixing: the last review's own security fix (symlink escapes in path-containment checks), its dead-code bug (`yaml-to-poem.js --all`), its stale register entry, its test-coverage gap in `build-blogger.js`, and its WCAG AA contrast findings are all confirmed independently resolved by this review rather than taken on trust — this session re-read the current code for each, not the prior review's verdict.

No Critical or High-severity findings were identified. The most notable finding is a genuine, if narrowly-scoped, security defect: `blogger-auth.js`'s OAuth loopback server reflects an unescaped `error` query parameter into its HTML response and skips the CSRF `state` check on that one branch, while the parallel success branch already gets it right (F-SEC-01) — bounded by the server's loopback bind and short one-shot lifetime, so rated Medium rather than higher, but a real asymmetry worth closing in a script whose entire job is guarding credentials. Beyond that, this review found a recurring pattern worth naming explicitly: several Medium/Low findings from the 2026-07-31 review (the README round-trip example, the missing human-facing contributing docs, a still-open `serve-static.js` architecture recommendation now three reviews running) remain unaddressed, alongside genuinely new findings this window — a second flaky-mtime test file the last review's fix didn't reach, an untested `sync-blogger.js` orchestration path that only runs for real in a consumer repo's production publish, inconsistent `--help` handling across the CLI tools, and three related gaps in the poem `$ref` caching subsystem. None of these are severe, and several (the OAuth reflection issue, the second flaky-test file) are exactly the kind of finding that only surfaces from independently re-verifying current code rather than trusting prior reviews or commit messages.

## Headline strengths

- Every automated check re-run this session — tests, lint, audit (with and without dev deps), coverage, licences, whitespace, tech-debt register consistency, and the build — passed cleanly from a fresh `npm ci`, not merely "configured to look green."
- Five of the last review's own findings (a security fix, a dead-code bug, a stale register entry, a test-coverage gap, and a WCAG AA contrast defect) are independently confirmed fully resolved this session, not assumed from commit messages.
- Security posture remains solid: no live secrets anywhere in the repo or its history, a textbook PKCE+CSRF OAuth flow (with one asymmetric branch — see F-SEC-01), masked credential prompts, 0600 atomic credential writes, and 0 dependency vulnerabilities.
- Architecture continues to avoid the shapes it could easily have grown into: no circular dependencies, no god objects despite some large files, and the riskiest cross-tool seam in the repo (`poem-to-yaml.js`/`yaml-to-poem.js`, under heavy round-trip-fidelity churn this window) is genuinely tested end-to-end rather than each side trusting its own assumptions.
- Accessibility work continues in good faith and correctly: three contrast/landmark fixes since the last review were independently re-verified against current CSS/JS/templates together, not just their commit messages, and all check out.

## Headline risks

- `blogger-auth.js`'s OAuth loopback server has an unescaped, unauthenticated HTML reflection and a missing CSRF check on its error path — bounded in blast radius, but a real asymmetry in a script whose job is guarding credentials [F-SEC-01].
- A second test file (`build-poems.test.js`) shares the exact mtime-comparison flakiness pattern a tech-debt item and PR already fixed in two sibling files, but didn't reach [F-TEST-01].
- `sync-blogger.js`'s `main()` and several helpers it alone calls are untested and never exercised by this repo's own CI — the only place that code path runs for real is a consumer repo's live Blogger publish [F-TEST-03].
- `--help` is inconsistently handled across `src/tools/`'s CLIs: two tools misread it as a filename and crash with a raw `ENOENT`, three more silently run their default action (including a real build) instead [F-UX-01].
- Several Medium-severity documentation and process gaps from the 2026-07-31 review remain open unchanged — the README round-trip example, human-facing contributing docs, and (now three reviews running) `serve-static.js`'s testability architecture recommendation [F-DOC-01, F-TOOL-01, F-ARCH-01].

## Scope and method

This is the sixth full review of this repository. Given five prior thorough reviews and a same-day-to-few-day tech-debt-resolution culture, this review's strategy was to (a) re-run every automated gate from scratch rather than trust prior results, (b) read the diff and every commit since the last review (2026-07-31, 20 commits) closely, verifying current file contents rather than commit-message summaries, (c) explicitly re-verify each of the last review's still-open Medium/Low recommendations against current code rather than assuming they remained accurate — several were found unchanged, one set of findings was found fully resolved, and one (the mtime flakiness) was found only *partially* resolved (fixed in two files, not a third), and (d) sample previously-reviewed, unchanged code rather than re-reading it line-by-line, treating prior findings as accurate unless this session's evidence contradicted them.

All thirteen checklist dimensions were covered by seven parallel subagents, each handed the project map and its assigned dimensions' checklist sections, followed by one lead-reviewer consolidation pass. Three dimensions — performance, observability, and data handling — were independently re-examined against their own specific surfaces (the poem-corpus build loop and `$ref` caching, the dev server and outbound API calls, and the Blogger OAuth credential surface respectively) rather than being waved through as inapplicable on the strength of prior reviews having said so; each turned up small, real findings this time (F-PERF-01/02, F-OPS-01/02) even though the overall dimension verdict — largely inapplicable to a CLI/build-tool project — is unchanged. The accessibility review (`npm run a11y`, wrapping axe-core via puppeteer-core) was directly attempted this session and, as in every prior review, could not execute a live automated check in this sandbox — no Chrome/Chromium binary exists and there is no root to install one — so UX contrast findings were derived from direct WCAG contrast-ratio computation against the generated CSS instead; this is narrower than a live axe-core run and is flagged as such. Dependency freshness (`npm outdated`, plus reading the actual markdown-it v15 changelog rather than assuming risk) and the live GitHub branch-ruleset state (`gh api`) were both checked with working network/API access this session.
